# Photographer Roadmap：摄影工作流应用后续规划

> 基于已有基础版本的需求路线图，整理于 2026-09-24。本文记录此前讨论中用户提出且未撤回的需求，并给出后续建议实现。它不是从零开发的规格书：每项工作应先核对现有实现，复用已完成的能力，再补齐缺口。标为“建议”的细节是工程落地方案，不代表用户已经指定了唯一实现。当前克隆到的 GitHub 仓库仅包含 `LICENSE`，基础版本代码尚未在此仓库中核对；因此本文不推断任何具体功能已经完成。仓库现有 `LICENSE` 为 Apache-2.0；第三方组件、模型权重和相机 SDK 仍须分别核对许可证。

## 1. 产品定位与目标流程

面向需要大量导入、选片、交给 Lightroom Classic（下称 LR）调色、回收成片并交付客户的摄影师。后续技术方向为 **Tauri 前端 + Rust 后端 + SQLite 本地索引**，具体以基础版本实际技术栈为准；已有能力优先延用。照片原件优先存于用户指定的本地磁盘或已挂载的 NAS/HDD；缩略图、代理图、AI 结果与数据库放在 SSD。应用即使暂时无法访问 NAS，也应能查看已缓存的相册、缩略图和元数据，并明确标注原件离线。

核心流程：

```text
连接相机 / 选本地文件夹 / 手选相机照片
  → 新建或选择相册 → 选择 RAW、JPEG 或两者
  → 预检重复与目标路径 → 复制并校验 → 入库与生成缩略图
  → 后台分析并打 AI 建议标签
  → 用户随时进入相册筛选、标星、打标、反选、删除/排除
  → 将星级等写入 XMP → 在 LR 筛选和调色
  → LR 导出 JPEG → 导回成片并关联原片
  → 在应用中查看原片/成片、必要时做基础编辑
  → 手动发布至百度网盘等渠道 → 得到可复制的分享链接
```

“选片”是贯穿相册管理的操作集合，不是导入时必须完成的一步。用户可以只导入，之后再根据 AI 标签批量处理。整个链路需要可中断、可恢复、可撤销，并尽量避免误删原件。

## 2. 导入、相册与存储

### 2.1 导入入口与交互

1. **相机自动导入**：检测到相机连接后给出导入提示；用户可设置自动打开导入页或在已配置规则下自动开始。首次导入先确定相册和目标目录。
2. **相机手动导入**：列出相机目录/缩略图，允许按日期、格式、文件名选择部分照片；仅导入勾选项。相机不支持文件列表或缩略图时，明确降级到系统挂载/读卡器导入。
3. **本地文件夹导入**：选择一个或多个目录，可设置是否递归扫描、复制还是移动。建议默认复制；移动必须单独确认并在校验完成后才移除源文件。
4. 三个入口都进入同一套“建立或选择相册 → 预览导入内容 → 去重决策 → 导入 → 后台处理”流程。支持只导 RAW、只导 JPEG、两者都导；视频可一起编目，独立于照片格式选项。
5. 记录每次导入批次、来源设备/目录、时间、成功/跳过/失败数、目标相册及逐文件结果。允许重试失败项；重复执行不会再复制已成功文件。

### 2.2 路径与命名

- 默认物理目录：`照片根目录/YYYY/MM/DD/相册名/`。日期默认取相册拍摄日期，可在导入向导中修改；跨日活动可按用户指定的相册日期归档，仍记录每张照片真实拍摄时间。
- 对相册名做跨平台非法字符过滤和重名处理；同一天同名相册不能无提示覆盖。内部使用稳定 `album_id`，目录名可以改，数据库关系不能靠目录名维系。
- 保留相机原始文件名；目标冲突时显示冲突并按规则跳过或追加可追踪后缀。不要仅靠文件名匹配原片、成片或判定重复。
- RAW+JPEG 同时导入时保留各自原文件和元数据，在界面中可以合并为一组拍摄记录，也可以展开查看各文件。后续导入另一种格式时能补到既有拍摄记录中。
- 建议原件目录、SSD 缓存目录、数据库位置分别可配置；数据库与缓存可重建，原件与应用产生的 XMP/编辑配方需进入备份策略。

### 2.3 去重与幂等

去重必须跨相册、跨导入批次生效：相机里仍保留上次拍摄的文件，再次导入另一个相册时也会自动识别。默认行为建议为“跳过复制，并在导入报告里列出”；用户可配置“询问”“在当前相册引用同一资产”或“保留第二份副本”。在同一相册已有关联时，引用操作不应重复生成记录。

建议两阶段判定：先用文件大小、来源稳定标识/相机路径、拍摄时间等做候选筛选；对候选流式计算强哈希（例如 SHA-256 或 BLAKE3），**最终按内容哈希确认完全重复**。文件名相同、时间相同或画面相似不能作为自动删除依据。RAW 和 JPEG 是不同文件，不能因同名认定重复；相似图检测属于独立功能。若源相机不提供稳定 ID，仍依内容哈希确认。数据库保存来源指纹、内容哈希、目标路径、导入批次和决策原因。

导入文件先写临时路径，完成后校验大小/哈希并原子更名，再提交数据库记录；失败/中断可继续。NAS 断线时暂停并保留任务状态，不把未完成文件标记为成功。预检应显示目标空间、预计大小和重复项；禁止导入过程悄悄覆盖现有文件。

### 2.4 HDD/NAS 与 SSD 缓存

- 原件存储目录可以是本地 HDD，也可以是操作系统已挂载的 SMB 共享。应用通过普通文件路径访问，不直接把 SMB 与百度/夸克网盘等同。
- SSD 保存 SQLite、各档缩略图、RAW 预览/代理图、视频海报/低码率代理（可选）、AI 特征与任务状态；缓存按容量上限和最近使用情况回收，不能回收唯一原件。
- 根目录记录卷标/挂载点等信息。NAS 断线或挂载路径变化时，展示“离线/需重新定位”；不要把暂时不可访问误判为用户删除。恢复连接后按需校验和修复索引。
- 支持已有目录“只建立索引”与“复制导入”两种模式。前者原件位置由用户管理；对文件被外部改名/移动，提供重新定位和增量重扫。

## 3. 相册管理与人工选片

“所有照片”和“相册照片”是两个主入口。可按相册、日期区间、相机/镜头、文件类型、RAW/JPEG、原片/成片、星级、颜色标签、自定义标签、人物、AI 质量标签、导入批次、是否离线、是否已交付等条件组合筛选。支持关键词、文件名和常见 EXIF 搜索；搜索结果能保存为智能视图。筛选作用于照片记录，用户可切换“按拍摄记录折叠”或“展开所有文件/版本”。

手动选片采用非破坏工作流：快速浏览、放大检查、对比同一组照片、快捷键打 0–5 星、颜色/自定义标签、接受/拒绝、批量更改；用户可以先按“闭眼风险”“疑似失焦”“相似连拍”筛选，批量打星与打标，再反选未保留项，进入待删除集合。删除默认先从相册排除或移入应用回收站；如果同一资产被其他相册引用，不删除物理文件。永久删除需要明确列出将删除的物理文件及其全部引用，并提供恢复窗口/备份提醒。

星级、颜色标签、选片状态分层保存：标准星级可同步 XMP；颜色标签可写 `xmp:Label`，但不同软件对标签名称/颜色的映射可能不同，需用户配置；应用专属的 AI 标签、导入批次、相册关系、工作状态保存在 SQLite。不要假设 LR 的旗标、集合、编辑历史能通过标准 XMP 完整互通。

## 4. Lightroom Classic 与 XMP 互通

- 对专有 RAW，星级/标签等可互通元数据写入同名 `.xmp` sidecar；对 JPEG/DNG 等允许嵌入 XMP 的格式，优先按格式规范嵌入或提供受控 sidecar 策略。`xmp:Rating` 使用 0–5；应用内部“拒绝”状态单独管理，避免与星级混淆。
- 应用写 XMP 时只改自己负责的字段，保留已有未知字段、LR 调色参数、关键字和其他命名空间；写前备份/原子替换，记录时间与内容指纹。若 LR 与本应用同时修改，提示冲突并让用户选择“读取外部改动/保留本地/逐字段合并”，不能盲目覆盖整份 XMP。
- LR 已导入照片后，外部修改 XMP 不一定会自动更新其目录；界面给出“在 LR 中从文件读取元数据”的操作提示。相反，LR 对原片做的星级/调色变动，也需要在 LR 写入 XMP 后本应用才能可靠读取。相关行为须按 LR Classic 实测。
- LR 导出 JPEG 时，若导出选项包含全部元数据，JPG 可保留星级；仅导出版权等精简元数据时可能没有。应用导回时读取内嵌 `xmp:Rating`，并可按关联的原片继承缺失的星级，但应记录“嵌入值/继承值”的来源。**星级不是原片与成片的匹配依据。**

建议提供一页“LR 交接检查”：导出/写入 XMP 的建议设置、外部改动冲突提示、LR 导出 JPEG 的建议命名方式和元数据选择。应用不承诺自动同步 LR 目录数据库，也不把 XMP 当作完整的 LR 工程文件。

## 5. 原片、成片与版本关系

用稳定的“拍摄记录/照片组”关联同一次快门的 RAW、机内 JPEG、LR 导出的成片 JPEG，以及应用内基础编辑产生的派生文件。**物理文件（asset）**、**逻辑照片组（photo_group）**、**相册归属（album_item）**、**版本/来源关系（asset_relation）**分开建模。同一原件可以被多个相册引用；同一照片组可以有多个成片版本，如网页小图、客户交付大图、重新调色版。

相册页提供“只看原片 / 只看成片 / 原片与成片对照 / 仅看尚无成片的原片”快捷视图；缩略图默认显示用户指定的首选版本。照片详情可一键在对应 RAW、机内 JPEG、成片和其他版本之间切换。原片标星、成片标星与相册级选片决定可以分别保存，界面标明哪个星级将写回哪一个文件，避免成片导回时覆盖原片状态。

外部导回成片：选择 LR 导出目录 → 扫描新增文件 → 先按导出命名模板、原片文件名、EXIF 拍摄时间、相机序列号/原始 ID（若有）生成候选 → 用缩略图感知相似度辅助排序 → 对歧义项让用户确认 → 建立显式 `derived_from` 关系。提供一次性批量匹配与规则保存；匹配结果落库，日后重命名不丢关系。派生 JPEG 没有可靠原片标识时不得仅凭同名或星级自动强关联。未匹配照片进入“待关联成片”。

推荐的 LR 导出命名模板包含原始文件名加版本标记，例如 `DSC_1234_edit_v1.jpg`；目录可选 `相册目录/成片/` 或独立成片根目录。用户无需为了建立关系强制采用单一目录结构。

## 6. 本地 AI 搜索、分类与辅助选片

全部默认在本机运行，不上传人脸、原图或嵌入向量。AI 输出只作为可筛选建议，用户保有最终决定；模型版本、阈值和分析时间一同入库，换模型后能后台重算。

| 任务 | 建议路线 | 输出与交互 |
| --- | --- | --- |
| 人脸发现与按人分组 | 小型检测模型定位人脸 + 人脸嵌入模型 + 向量聚类；起步可评估 OpenCV Zoo YuNet + SFace | 人物候选、置信度、人工合并/拆分/命名；低质量侧脸单列待确认 |
| 闭眼检测 | 对已检测人脸裁剪，使用眼部关键点/眼睛状态小模型；对遮挡、眨眼、侧脸输出“不确定” | “有人闭眼”“可能闭眼”“无法判断”，允许按人物和单张查看 |
| 失焦/模糊 | 图像梯度/局部清晰度作快速筛选，辅以学习式质量模型；结合对焦主体/人脸局部判断 | “疑似失焦”及可解释热区；运动模糊、浅景深和背景虚化单独处理 |
| 相似/连拍选片 | 时间窗口 + 感知哈希/视觉嵌入分组，组内综合清晰度、人脸状态、构图等排序 | 相似组候选与组内推荐；绝不自动删除 |
| 语义搜索/分类 | 小型图文嵌入模型，图像向量离线入库；中文查询先实测模型能力或做本地翻译 | 文本找图、视觉相似检索、可确认的主题标签 |

质量链路建议为“RAW 内嵌预览/相机 JPEG → 标准尺寸代理图 → 人脸与画质分析 → 写 AI 标签 → 用户复核”。不要拿全分辨率 RAW 对每张照片重复解码。人脸聚类阈值需按实际照片集校准，支持未知人物和误合并纠正；闭眼检测需在不同年龄、眼镜、侧脸、多人合照上实测。失焦是主观与场景相关判断，不能只用 Laplacian 阈值直接判定废片。AI 推荐星级与用户实际星级分开存，只有用户显式接受才同步进 XMP。

**选型原则**：优先 ONNX Runtime 等跨平台推理后端，并使用 CPU 可运行的小模型；GPU 加速为可选。准确度优先时，可替换更强的人脸嵌入、眼部状态和画质模型，代价是包体、内存和耗时增加。做本项目自己的测试集，按误检/漏检、低光、肤色、侧脸、眼镜、RAW 品牌和硬件平台记录结果；不要以“模型参数量小”直接推断准确度。任何候选模型都要分别核对**代码、权重、训练数据/使用条款**。

## 7. 相机联机拍摄与最大兼容范围

Rust 实现统一的 `CameraBackend` 抽象：发现设备、列出存储、读取缩略图/文件、订阅新文件事件、触发拍摄、获取预览、取消任务、断线恢复。每个能力由后端报告 `supported/unsupported`，界面按能力显示操作，不假设所有相机都支持联机拍摄或实时取景。

按覆盖面分层：

1. **文件导入通道**：读卡器/USB Mass Storage/系统挂载目录，跨平台且适用面广；提供自动监控新文件和手选导入。
2. **通用相机通道**：优先评估 `libgphoto2` 的 Rust 绑定，用于 PTP 及其厂商扩展可支持的设备；在 Linux/macOS 重点验证，在 Windows 单独验证驱动安装、设备占用与打包。用其相机能力列表而非品牌名承诺具体功能。
3. **操作系统设备通道**：对 Windows WPD、macOS Image Capture 等系统可访问的设备，按平台实现导入适配器，补足文件传输覆盖；联机拍摄能力另测。
4. **厂商 SDK 插件**：仅在通用后端不满足的机型上接入，用于拍摄控制、事件、实时取景等。它们通常是 C/C++ API + USB/PTP 厂商扩展或网络连接，不存在统一的“厂商 SDK 协议”。每家 SDK 的可分发性、平台支持、架构、动态库许可和机型清单分别核查；不能因为 Rust FFI 可调用就假设可随开源应用再分发。

同一相机可能被操作系统导入服务、LR 或本应用占用；对独占和断线给出明确提示。跨平台最小承诺应是“可通过已挂载存储/读卡器导入”；遥控拍摄、实时取景、机内文件浏览按已验证机型公布能力矩阵。首批开发应取 Canon/Nikon/Sony/Fujifilm 等常见机型样本，分别验证连接、手选下载、拍摄事件、RAW+JPEG、断线、长时间拍摄以及 Windows/macOS/Linux。

## 8. 基础编辑与导出

应用无需完整调色能力。仅实现裁剪/旋转（作为裁剪操作的一部分）、添加文字、画笔标注、输出尺寸调整、元数据编辑和导出 JPEG。编辑默认非破坏：保存裁剪矩形、文字/画笔图层、输出尺寸等“编辑配方”，预览时实时合成；导出才生成新 JPEG，并作为原片/成片组中的一个派生版本。允许撤销/重做和重新编辑；保留输入文件及其拍摄元数据。

导出选项包括像素尺寸/长边、质量、颜色空间（默认 sRGB）、输出目录与文件名、是否保留/移除 GPS、版权/作者/关键词等元数据。写元数据时区分“修改本应用数据库”“写入 XMP”“写入导出 JPEG”，让用户知道哪些字段会影响原件。照片处理推荐在 Rust 后台线程执行，使用成熟图像库做缩放、裁剪和编码；RAW 解码/预览由专门解码库负责。文字渲染要随字体许可证和跨平台字体差异做测试，画笔笔迹采用标准化坐标以支持输出时重放。

## 9. 视频浏览与嵌入预览

视频与照片共用相册、日期、标签、星级、来源和去重框架，索引视频时提取时长、尺寸、帧率、编码、码率与封面。支持预览高码率原素材，包含时间轴拖动、音量、全屏和关键帧海报；优先尝试硬件解码，解码失败或 NAS 吞吐不足时可生成本地代理文件供流畅选片。原件一直保留，播放代理与播放原件的状态要清晰显示。

可评估 `libmpv` 作为解码/播放后端。它可以嵌入应用，但在 Tauri 的 WebView 中无缝显示需要原生子视图、渲染 API/纹理桥接或平台窗口句柄方案；不同系统的层叠、缩放、输入焦点和全屏都需原型验证。不要把“能创建 libmpv 窗口”当作“已经可靠嵌入 Tauri 页面”。视频依赖的 mpv/FFmpeg 实际打包许可证和编解码器许可另行审计。

## 10. 网盘与交付

日常管理采用本地/NAS 原件 + SSD 缓存，不以百度网盘或夸克网盘直接挂载作为核心工作盘。消费级网盘是否提供稳定、官方、适合第三方应用的 SMB/WebDAV/开放 API，按具体服务和时间核查；即使可挂载，也不能假设其随机读、缩略图批量访问与断点续传性能适合百万级选片。

**网盘是用户手动选择的发布/交付动作**：在相册或选中照片上右键“发布到…”；选择原片、成片或指定版本，设置文件夹和命名，预览总量，启动后台上传；显示进度、失败与重试；成功后创建分享链接并复制、记录到相册交付记录。优先做百度网盘适配器，其他网盘以后逐个增加。每个网盘适配器负责登录授权、上传/续传、创建分享、链接有效期、权限和错误处理；仅使用获准且稳定的官方接口。若某网盘不开放必要能力，则提供“导出到本地交付目录，由官方客户端同步”的替代流程，不承诺能自动返回分享链接。

交付记录保存发布对象的 `asset_id`/版本、上传时间、远端路径/文件 ID、分享链接及有效期；隐私敏感的令牌存系统凭据库，不进 Git、日志或普通 SQLite 明文。分享链接失效时允许重新生成；重新发布同一成片默认提示“覆盖/新版本/跳过”。

## 11. 技术架构与性能

### 11.1 组件边界

```text
Tauri WebView UI
  ├─ 相册/导入/选片/原片成片/搜索/发布界面
  └─ 只请求当前可视区的列表、缩略图和操作结果
Rust 应用服务
  ├─ 导入任务与去重 ├─ 相机适配器 ├─ 文件/元数据/XMP
  ├─ 缩略图/视频代理 ├─ AI 分析与搜索 ├─ 编辑导出
  └─ 网盘发布适配器
SQLite（SSD）：索引、关系、任务、AI 结果、用户状态
照片原件（本地 HDD / 已挂载 NAS）：RAW、JPEG、视频、XMP、成片
SSD 缓存：缩略图、预览、代理、必要的向量索引
```

前端大量图片的主要瓶颈通常是 DOM 数量、缩略图解码/上传纹理、WebView 内存、滚动时重复请求以及跨 NAS 随机读取，而不是 SQLite 单次索引查询。网格使用虚拟滚动，只渲染可视区及小范围预加载；固定尺寸缩略图、多档缓存、异步加载与取消、请求去重、滚动方向预取。缩略图通过受限本地资源协议或 Tauri 自定义协议提供，不把原始大文件转成 base64 反复跨 IPC。查看单张时先显示缩略图，再升级为预览/原件；后台任务限流，避免导入与 AI 分析抢占交互带宽。

SQLite 百万级记录可作为本地索引基础，但要按实际查询设计联合索引和分页；例如 `album_item(album_id, sort_time, asset_id)`、`asset(content_hash)`、`asset(capture_time)`、`asset(kind, rating, capture_time)`。文本搜索可用 FTS5；人脸/图像向量先单独管理或选用经过验证的向量扩展。使用 WAL（同时注意 NAS 上数据库不应直接放共享目录）、批量事务、预编译语句和键集分页，避免大 `OFFSET` 翻页。建立百万级模拟数据与真实照片样本基准，分别测首屏、相册切换、复合筛选、滚动和 NAS 离线场景；不要给没有数据分布和硬件条件的固定毫秒承诺。

### 11.2 建议的核心数据表

| 表/实体 | 关键字段及职责 |
| --- | --- |
| `storage_root` | 路径、设备/共享标识、在线状态、缓存策略 |
| `album` | 稳定 ID、名称、相册日期、目标目录、封面 |
| `import_batch` / `import_entry` | 来源、格式规则、去重策略、任务状态、逐文件结果 |
| `asset` | 稳定 ID、路径、格式、大小、内容哈希、拍摄时间、EXIF、离线状态 |
| `photo_group` / `group_asset` | 一次拍摄的逻辑组及其 RAW、机内 JPEG、成片成员 |
| `asset_relation` | `derived_from`、来源软件、版本号、匹配依据和确认状态 |
| `album_item` | 相册与资产/照片组关系、显示顺序、相册级选片状态 |
| `rating_label` | 星级、颜色标签、用户自定义标签及写回状态 |
| `face` / `person` / `embedding` | 人脸框、向量、聚类、人工命名和模型版本 |
| `ai_analysis` | 闭眼/失焦/相似组/主题建议、置信度、复核状态 |
| `edit_recipe` / `export_job` | 非破坏编辑、导出参数、派生资产 ID |
| `delivery_job` / `delivery_link` | 上传进度、远端对象、分享链接、有效期 |

数据库迁移按版本管理；大字段、缩略图和原图不放入 SQLite。所有后台任务可取消/重试，写入有幂等键；任务状态从进程重启后恢复。

## 12. 开源与商用风险

“免费”和“开源”不等于“允许商用或再分发”；即使应用本身公开在 Apache-2.0 仓库中，也不能自动覆盖第三方模型权重、SDK、字体、编解码器或云服务接口。用户是否用软件处理收费照片，是使用场景；项目是否把受限组件打包、提供下载或依赖其完成核心功能，是另一项许可问题。发布前保留逐依赖的 SPDX/许可证清单、版本与下载来源，并审计实际发布包。

| 组件/来源 | 当前风险与处理 |
| --- | --- |
| 仓库代码 | 现有 `LICENSE` 为 Apache-2.0；新增代码按项目许可证管理，保留第三方声明。 |
| OpenCV Zoo YuNet/SFace | 仓库与模型目录可作为优先候选，发布前锁定具体权重文件、许可证与来源并归档。 |
| InsightFace | 代码许可与公开预训练权重许可不同；其公开模型注明仅限非商用研究，不能把 `buffalo_*` 当作可自由商用的默认模型。 |
| `libgphoto2` / Rust 绑定 | 核对实际绑定和原生库的许可证及动态链接/分发义务；它不解决厂商 SDK 的授权。 |
| LibRaw | 上游提供 LGPL-2.1 / CDDL-1.0 双许可证选择；记录选用条款、构建方式和发布物。 |
| 厂商 SDK | 每家单独检查下载协议、允许平台、重新分发、开源发布兼容性；不合适时做用户自行安装的可选插件，或不上架该后端。 |
| `libmpv` / FFmpeg | mpv 默认构建可能包含 GPL 代码，也存在有条件的 LGPL 构建；FFmpeg 的实际构建开关及链接库进一步影响发布义务。 |
| AI 权重和训练集 | 模型代码、权重、训练集、下载页条款逐一审核；不能仅凭 GitHub 仓库根许可证推断权重可商用。 |
| 网盘 API | 只接官方允许的接口，核查开放平台条款、分享链接生成限制、调用频率及品牌使用要求；定期重新验证。 |

建议仓库增加 `THIRD_PARTY_NOTICES.md` 与机器可读依赖清单；CI 检查新依赖/模型是否有许可证记录。首次公开发布前由项目维护者或法律顾问核对实际二进制构成、权重和 SDK 条款。这里是工程风险清单，不是法律意见。

## 13. 实施顺序与验收

### 阶段 0：盘点现有基础版本

将基础版本代码和构建说明纳入仓库或明确其源码位置；核对现有的 Tauri/Rust/SQLite 结构、导入入口、相册/文件数据模型、缩略图、选片、元数据、视频与发布能力。对照本路线图标记“已有且可复用 / 需改造 / 尚未实现”，保留既有用户数据并设计数据库迁移。先补最短的真实工作流回归验证，再决定阶段 A–D 的具体任务和顺序；不要为已有功能重复搭建一套平行实现。

### 阶段 A：可用的本地照片管理

在基础版本上补齐或改造相册、文件夹/读卡器导入、RAW/JPEG 配置、目录规则、跨相册内容去重、SSD 缩略图缓存、百万级分页浏览、基础筛选、星级/标签、XMP 写回、导入任务恢复。验收：相机卡上保留旧照片再次导入新相册时可按规则跳过；NAS 断线不丢索引；LR 能看到写入的星级；重新启动后任务可恢复。

### 阶段 B：选片、成片关系和本地 AI

完成批量选片/回收站、原片与成片分组、LR 成片导回与批量关联、人脸分组、闭眼/失焦建议、相似连拍组、文本/相似图搜索。验收：只导入后仍能按 AI 标签筛选、批量标星、反选排除；LR 导出成片回导后可在原片/成片视图切换；误匹配能人工修正且重启后保持。

### 阶段 C：相机联机、视频与编辑

先验证 `libgphoto2` 和各平台系统设备通道，再按机型加厂商 SDK 插件；加入视频海报/代理、`libmpv` 嵌入原型、非破坏基础编辑和 JPEG 导出。验收：公布实测机型/平台/功能矩阵；高码率视频可在应用内预览或明确回退代理；编辑导出不改原件。

### 阶段 D：网盘交付

实现“手动发布”统一接口、百度网盘适配或官方客户端同步回退、进度/重试/交付记录/分享链接。验收：原片和成片可分别选择交付；上传中断可恢复；链接有效期和远端状态可查看；API 不可用时仍能完成本地交付目录导出。

阶段顺序是实现建议；每阶段先做 Windows/macOS/Linux 构建验证，再用真实相机、真实 NAS 和真实 LR 工作流做端到端试用。性能指标以试验环境、样本量和可复现脚本记录，不凭空承诺“所有相机”“所有 RAW”或固定查询时间。
