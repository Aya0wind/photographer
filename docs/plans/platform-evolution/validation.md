# 验证、兼容与交付矩阵

返回 [方案入口](README.md)。本文件规定未来改造的验证范围，不表示这些测试已经执行。阶段状态见 [roadmap](roadmap.md)。

## 1. 测试跟随职责

单测验证一个模块的规则和失败语义，贴近实现；集成测试验证协作边界，放到其覆盖范围的最小共同层级。不为移动文件增加只验证同一实现表达式的测试，优先迁移已有用例并覆盖真实风险。

```text
crates/media/
├── src/...                      # 单测随 Rust 模块 / #[cfg(test)]
└── tests/                       # media 的解码、配方、渲染与输出集成
components/editor-core/
├── src/.../*.test.ts            # 配方、坐标等相邻单测
└── tests/                       # 本 component 的跨模块集成
apps/desktop/
├── .../editor/tests/            # 仅覆盖 app 编辑器子系统的集成
└── tests/                       # 桌面装配与应用级端到端
apps/mobile/tests/               # 手机装配、系统照片与生命周期
apps/web/server/tests/           # 服务/API/存储/worker 的集成
apps/web/frontend/...            # 页面相邻单测与 frontend 自身集成
apps/web/tests/                  # 确实跨 server/frontend 的流程
tests/                          # 仅出现跨产品验证时创建，如服务与原生客户端同步
```

目录名是职责示例，不预先创建空目录，也不锁定测试框架。fixture/helper 与测试放在同层或其实际共同上级；tools 只提供执行/生成入口，测试断言仍归所属模块。

现有测试优先保留：如 `src/features/editor/lib/recipe.test.ts`、`previewScheduler.test.ts` 跟随逻辑移动；`src-tauri/tests/edit_export_test.rs` 按 media 渲染与 app 输出登记职责逐步拆分，不能迁出后漏掉原来的应用集成覆盖。导入恢复、数据库切换与任务 supervisor 现有用例也应跟随真实消费者。

## 2. 基线、样片与兼容对照

M0 建立样本清单，记录来源使用权限、文件 hash、相机/格式、分辨率、方向、ICC/EXIF、配方/渲染版本、LUT/字体等资源版本和已知限制。小型合成数据用于边界与数值测试；真实 RAW 用于相机/内存/画质验证，两类不能互相替代。

代表样本覆盖普通 RGB、带 ICC/方向的图片、高位深/透明图、至少具有不同传感器/相机特征的 RAW、负值/超白、肤色/灰阶/饱和色、缺失资源及旧配方。实际机型覆盖根据可获得样片登记，不把有限样本结论推广为所有相机可用。私有照片和大型 RAW 不直接提交仓库；通过有权限的本地/CI fixture 获取，保留可复现清单。

比较规则：

- 纯目录/边界迁移且后端、输入和设置相同时，优先要求确定性路径像素一致；文件容器时间戳等差异单独分析。
- CPU/GPU 或显影合同不同的路径，比较工作值、图像差异和关键区域；容差由 M0 样本/数值分析确定，不能为迁就失败任意放宽。
- 旧配方默认值、未知字段、资源引用、保存后重开和撤销历史各有对照；新渲染版本不自动重解释旧项目。
- 原图 hash、数据库资产/相册/版本关系、元数据与导出登记也需要核验，不能只有截图相似。
- 新 LibRaw 的效果不同于旧显影不必然是 bug，但必须符合新合同并保留版本选择；JPEG 切换色差要与错误重复曝光/WB/gamma 区分。

## 4. 实时、并行与 fallback 场景

性能目标和分段定义以 [realtime](realtime.md) 为准。记录输入到实际可见帧的分位数、稳定帧率、排队与峰值 RAM/VRAM，不能用 GPU 提交成功或平均算子时间替代。指定设备/OS/驱动、原图/代理尺寸、线程数、质量等级和冷热缓存。

关键场景包括连续拖动时后台代理完成、切照片后旧帧返回、白平衡精确更新、蒙版与几何同时修改、窗口/表面销毁重建，以及缩略图/AI/导出并行时前台响应。关闭会话后的资源必须最终释放；不可中断原生调用退出前仍应计入预算。

Auto、CPU、Force GPU 分别验收无适配器、缺失能力、初始化失败、设备丢失与资源不足。可恢复失败的 Auto 回退必须报告实际后端；Force GPU 不得静默 CPU。仅 fault injection 的结果不等于真实驱动故障验证；native 崩溃也不能由 Rust panic 用例证明已隔离。

CPU/GPU 对照覆盖色彩范围、Log 分段、LUT 边界/强度、固定颗粒种子、瓦片边缘/halo、源像素尺度与导出。性能回归与图像误差分别报告，降分辨率或简化效果要明确质量状态，不能暗中改变配方含义。

## 5. 服务与同步失败矩阵

| 类别 | 必须覆盖的失败 | 核验结果 |
| --- | --- | --- |
| 作用域 | 用其他工作区 ID 读取原图/缩略图/代理/LUT/AI/导出/事件 | API、资源与缓存均不泄漏其他范围内容 |
| 并发 | 两用户以同一基础 revision 保存 | 事务只接受符合前置条件的更新，冲突稿可找回 |
| 重试 | 服务已提交但回执丢失、分块重复、同内容再次上传 | operation_id 可恢复回执，登记和副作用不重复 |
| 任务 | worker 在输出/登记之间退出、服务重启、浏览器关闭 | 租约与持久状态恢复，不产生错误成功或孤立登记 |
| 增量 | 游标过期、快照与增量并发、乱序/重复事件 | 重建一致状态并保留未提交 journal |
| 权限 | 同步中撤权、退出/切服务器、凭据过期 | 后续访问被拒绝，身份映射隔离，本地独立照片不受误删 |
| 删除 | 远程 tombstone 与本地离线编辑同时发生 | 冲突可处理，缓存/受管副本/本地原件删除语义不混用 |
| 恢复 | 手机进程终止、系统文件授权失效、缓存被清理 | 可重新授权/下载/继续，失败原因明确，已确认版本不倒退 |
| 公平性 | 大 RAW/AI 批任务与交互请求争用 | 单用户不能占满全局许可，队列/配额有诊断证据 |

使用两个用户、多个工作区和独立本地库验证，不能仅用同一账户两个浏览器标签页代替。文件系统/对象存储中的结果也要检查，不能只验证 HTTP 状态码。

## 6. 构建与发布门槛

按实际 app、target、feature 组合建立构建矩阵；共享改动触发其消费者检查。每个宣称支持的产品必须有 CPU 路径证据，GPU 能力按设备验证；不以一次 workspace all-features 构建代替 Windows/macOS/Linux、Android/iOS 和 Linux 无头环境。

服务构建不得拉入托盘、联拍、窗口或桌面设备 SDK。原生 C/C++ 的 SDK/ABI、依赖版本/补丁、模型与 LUT 资源需可追溯；分发所需许可证及资源清单随对应产品维护。交叉编译通过只证明产物可构建，不能证明真机颜色、权限、内存和生命周期正确。

正式服务部署需验证备份恢复和升级失败路径。本地未发布 schema 的处理遵守 [模块迁移](module-migration.md)，不因目录重构增加历史兼容框架，也不默认销毁现存开发数据。若新数据不能由旧程序读取，要明确数据恢复方法，不能只提供二进制回退命令。

一次交付记录至少包括：commit/锁定依赖、改变的边界、使用的命令与环境、样片/数据集、结果与差异、资源/性能数据、未验平台和限制。源码阅读、静态检查、构建、自动化测试、真机交互分别标记。

## 7. 本轮文档交付的检查范围

只检查文档路径、相对链接、阶段编号、已确认与待定事项、职责和兼容说明一致性，并核验 Git diff 未包含应用源码改动。本轮不运行应用、构建或业务测试；上述矩阵是实施要求，当前均不作为“已通过”的功能证据。
