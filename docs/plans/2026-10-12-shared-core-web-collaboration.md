# 桌面、手机、Web 服务版的复用边界与多用户协作计划

日期：2026-10-12。状态：待实施。本计划扩展并约束 [移动共用核心抽象计划](2026-10-12-mobile-core-abstractions.md) 与 [LibRaw/Smart Preview/胶片计划](2026-10-12-libraw-smart-preview-film.md)；当前只修改文档。

本文件保留方案收敛过程。当前方案已按职责拆分到 [多形态应用与共享核心实施方案](platform-evolution/README.md)，包含代码组织、模块移植、实时计划、协作同步、统一 roadmap 与验收矩阵；后续实施顺序和决策状态以新目录为准。

## 0. 当前定案范围

本轮收敛大致工程方案：代码放在哪里、哪些能力共享、谁依赖谁、各产品怎样装配、按什么顺序改造。暂不逐项敲定接口签名、方法名、字段布局或底层库选型；这些在实施对应模块时结合实际调用与性能原型细化，影响架构的选择再由用户定夺。

| 已确认事项 | 方案 |
| --- | --- |
| 产品与模式 | 单仓内桌面、手机、Web 三种产品；桌面/手机本地单用户，也可连接服务器协作；协作权威在服务端 |
| 存放 | apps/desktop、apps/mobile、apps/web/server、apps/web/frontend；共享 Rust 放 crates，TypeScript 放 components，C/C++ 放 native，工程脚本放 tools |
| 语言与性能 | Rust 为主，允许 C/C++；脚本不承担常规应用运行时；原生多核/SIMD/GPU 友好、减少复制、统一预算并有 CPU fallback |
| 引用 | 一个 Cargo workspace，仓内 path 依赖、共用锁文件；components 通过公开包入口直接消费源码 |
| 模块 | 按 model/media/catalog/runtime/protocol/sync 及已有 AI/metadata/geo/存储/导入能力拆 crate，逐个提取，不创建空壳 |
| 依赖 | §2.7 的单向依赖；纯模型/协议不带重型依赖，应用服务装配跨能力流程，具体实现依赖使用方定义的接口 |
| 测试 | 单测贴近实现；集成测试放到能覆盖职责的 crate/component/子系统/app 层；真正跨边界的验证才放共同上层 |
| 改造 | 保留已有算法和成熟流程，沿一条可用流程逐步迁移；桌面持续可用，无头服务/手机原型提前验证 |

文中尚未落地的类型名、协议字段、数据库候选和后端方案用于说明职责，不是本轮已经确认的签名或实现。`asset-io` 独立 crate 仅为讨论候选，暂未定案；当前只确定资产访问要隔离本地文件、系统照片和远程来源，供缩略图、元数据、显影和 AI 复用。

具体各端功能裁剪、前端包管理工具、应用版本发布节奏、原生依赖源码/构建缓存策略，以及 GPU/存储/网络框架选择都留待对应实施阶段讨论，不阻塞当前架构概要成立。

## 1. 产品形态与范围

独立应用按产品形态划分，不按操作系统划分：

| 产品形态 | 目标 | 形态内部的适配 |
| --- | --- | --- |
| 桌面版 | 单用户本地工作台；也可作为完整客户端连接服务器 | Windows/macOS/Linux 平台适配、本地与远程会话隔离 |
| 手机版 | 单用户本地应用；也可作为客户端连接协作服务器 | Android/iOS 来源、生命周期、GPU 和权限适配；复用远程协议与同步逻辑 |
| Web 服务版 | Linux 照片管理、多人协作与本地客户端同步服务；浏览器功能受限 | 无头处理、网络 API、用户/工作区、异步编辑任务和同步协议 |

Web 服务版以照片管理和多人协作为主，不建设本地工作台，不要求实时编辑预览；不启动联机拍摄、托盘、窗口和移动照片库服务。按本轮“必须要有高级编辑器”的要求，保留高级编辑能力，采用配方编辑后异步生成预览/成片的方式，复杂高频交互优先由桌面客户端完成。浏览器受限不等于后端丢弃桌面配方字段。

多人协作的权威实现属于服务器版本。桌面/手机本地模式不增加成员、协作权限和共享历史；二者连接服务器时都是远程客户端，由服务端负责权限与并发。采用单仓多应用，各产品独立构建和发布；应用入口与宿主适配分别组织。共同的算法、参数合同和业务规则优先复用。

具体各端的功能裁剪后续商议；下表表示模式与职责，不是最终发布功能清单。能力合同允许客户端查询实际支持的操作；不因手机版资源较少而直接认定它不能协作。

| 能力 | 桌面本地 | 手机本地 | 桌面/手机连接服务器 | 浏览器访问服务器 |
| --- | --- | --- | --- | --- |
| 本地实时高级编辑 | 保留 | 保留 | 在已授权、可本地读取的代理/原图上执行 | 不要求；配方编辑与异步预览 |
| 照片管理 | 本机数据库 | 本机数据库 | 服务端工作区加本地可重建缓存 | 服务端工作区 |
| 用户/成员/多人协作 | 无 | 无 | 调用服务端功能，无本地协作权威 | 服务端提供 |
| 原图/配方同步 | 不连接时无需同步 | 不连接时无需同步 | 可选择缓存/原图上传下载、离线修改后提交 | 直接操作服务端资源 |
| 联机拍摄及设备工作台 | 依桌面需求保留 | 本计划不要求 | 不将本机设备服务公开给服务器 | 排除 |

“多用户写作”按多用户协作解释：共享图库/相册、个人与共享编辑版本、权限、并发保存、任务及结果归属。首期不承诺多人同时拖动同一条曲线或共同绘制一笔；先实现可预测的版本冲突与共享流程。

## 2. 已确认的仓库组织与候选组件边界

2026-10-12 brainstorming 决定 01：采用 A，单仓多应用。共享组件、桌面应用、手机应用、Linux 服务与浏览器客户端存放在当前同一仓库，各产品独立构建和发布。决定 02：应用后端与处理核心以 Rust 为主，允许 C/C++ 原生组件。决定 03：采用 §2.2 的顶层布局与测试归属规则。决定 04：按 §2.3 沿用现有能力边界、逐步提取。决定 05：采用 §2.4 的统一 Cargo workspace。决定 06：采用 §2.5 的 TypeScript 源码消费方式。决定 07：采用 §2.6 的按能力拆 crate 方式。决定 08：采用 §2.7 的依赖方向。具体接口与工具在实施对应模块时细化；下表早期逻辑组件由后续职责与 crate 划分细化，不创建同名万能包。

| 候选逻辑组件 | 放什么 | 不放什么 |
| --- | --- | --- |
| `photographer-core` | 多个职责明确的 Rust crate：配方/参数合同、纯图像数学、胶片/色彩、渲染准备、可选 PhotoCraft/LibRaw 适配 | Tauri、HTTP、窗口、系统照片 API、登录、成员关系、用户权限、部署配置 |
| `photographer-client` | API 契约、远程传输、同步状态/冲突合同及确实共用的逻辑；桌面/手机复用同步模块，预览调度独立可选 | 强制统一三种产品全部页面、强迫本地模式登录、直接散落的路径访问 |
| `photographer-desktop` | 当前项目演进后的本地产品，加远程连接/同步适配；本地工作台和服务端工作区隔离 | 每个桌面 OS 独立产品仓库、本地实现服务器的成员/权限权威 |
| `photographer-mobile` | 一套手机产品，共享 Android/iOS 上层逻辑与远程客户端能力，各自原生适配 | 将 Android 与 iOS 拆成两个业务产品、本地实现服务器权限权威 |
| `photographer-web` | Linux 服务、权限/工作区、协作/同步 API、异步图像 worker、功能受限的浏览器客户端及部署 | Tauri/WebView 运行时、设备服务、桌面窗口、浏览器本地实时图像引擎 |

在当前仓库建立模块/包边界，应用使用独立入口。共享包提取由实际调用方驱动，在至少两个消费者中验证；产品差异由组装决定。没有预定拆仓步骤，也不使用长期产品分支复制共享算法。

Rust 同仓共享源码采用 §2.4 的 workspace/path 引用，TypeScript 采用 §2.5 的源码消费方式；外部依赖保持可复现，协议和配方记录兼容范围。共享组件改动验证受影响消费者；网络接口不兼容要版本化。分支服务于开发，不作为永久平台产品复制机制。

### 2.1 已确认的技术前提

以下是用户确定的约束，具体库、线程池、GPU 后端与扩展机制继续逐项定案。

- **原生实现：** 应用后端、业务核心和图像处理以 Rust 为主，可使用 C/C++ 实现或接入原生能力。Python 等脚本用于项目管理、构建、生成和离线工具，不作为常规应用服务或图像执行运行时。未来若为扩展引入脚本语言，单独确定扩展接口与执行边界。浏览器/现有客户端前端仍可使用 TypeScript，不能把原生处理要求误解为禁止必要的前端语言。
- **可扩展接口：** 为新的来源、输出格式、像素格式、设备能力、处理后端与扩展预留位置。以版本、能力查询、可选配置、明确的未知值/不支持行为实现扩展空间；C ABI 可采用结构大小/版本检查。跨版本保留未编辑配方字段的合同独立验证，不以任意 JSON 贯穿图像计算。具体保留字段与 ABI 形式在接口设计时确认。
- **直接的热路径：** 配方解析/校验在控制路径完成，转为类型化参数与处理计划；逐像素循环不经过 JSON、RPC、脚本或通用动态命令解释。抽象停留在数据批次、阶段或后端边界，避免逐像素虚调用与反复全图格式转换。
- **原生并行友好：** 图像表示明确所有权、尺寸/步幅、像素/色彩格式和可变区域；使用可划分的行带/瓦片与不重叠输出，保留邻域 halo、源坐标及随机种子语义。优先 SIMD、批量计算与多核执行，减少分配、复制和全局锁；小图/短任务允许串行以减少调度成本。
- **统一资源预算：** Rust 线程池、C/C++ 库线程、LibRaw/OpenMP、编解码和 AI 不各自占满全部核心。重任务由宿主资源预算协调，前台交互、多用户公平和手机温度/内存约束都纳入；不在像素循环中频繁跨语言调用。
- **GPU 优先评估：** 对可获益的阶段提供 GPU 路径，保持源纹理/中间结果常驻，尽量批量提交、复用缓存并减少 CPU/GPU 往返。后端按实际设备能力选择；大图要考虑纹理/缓冲限制与分块，性能以端到端可见帧或完整任务时间验收。
- **明确回退：** 合同区分自动选择、CPU 和强制 GPU。自动模式在设备/功能不支持或可恢复失败时可回退 CPU，记录实际执行后端；强制 GPU 不能把 CPU 成功伪装成 GPU 成功。CPU 基线保持可用，GPU/CPU 维持同一色彩/尺度语义与经验证的误差范围。回退先确认失败 GPU 任务和资源的状态，避免 CPU 与未结束的 GPU 重活同时超额占用。
- **按证据优化：** 在代表图片、不同设备和并发条件下记录冷/热耗时、内存/显存峰值、复制/上传/读回、线程利用与回退原因。极致性能目标同时包含正确性和真实端到端效果，不以单个内核 benchmark 代替整体结果。

这些前提不自动确定所有阶段均使用 GPU，也不要求先做完整插件框架。每项具体结构与技术选择在 brainstorming 中由用户确认后进入实施计划。

### 2.2 已确认的顶层布局与测试归属

```text
photographer/
├── apps/
│   ├── desktop/          # 桌面产品，内部适配 Windows/macOS/Linux
│   ├── mobile/           # 手机产品，内部适配 Android/iOS
│   └── web/
│       ├── server/       # Rust 服务、协作、同步与任务
│       └── frontend/     # 浏览器应用
├── crates/               # 共享 Rust 库
├── native/               # 项目维护的 C/C++ 核心、桥接及构建
├── components/           # 共享 TypeScript 契约、逻辑和界面组件
├── tools/                # 构建、生成、管理、基准工具
└── docs/                 # 设计、接口合同与实施计划
```

Web 浏览器应用命名为 `frontend`；共享 TypeScript 包的顶层目录名为 `components`，其职责包括非 UI 的契约与逻辑。目录不自动等于独立发布包；具体包边界后续确认。

测试分为单元测试和集成测试，按被测职责的最小完整范围放置：

- 单元测试贴近实现。Rust 可使用源码内 `#[cfg(test)]` 模块或相邻测试模块；TypeScript 使用相邻的 `*.test.ts`/`*.test.tsx`；C/C++ 测试归对应原生模块。
- crate 的公共合同/模块组合测试放在该 crate 的 `tests/`；component 的集成测试放在该 component 的 `tests/`。
- app 内某一子系统的集成测试放在该子系统所拥有的测试目录；涉及整个 app 的端到端或宿主集成测试才放在 app 的 `tests/`。
- 涉及 Web server 与 frontend 的组合测试可放在 `apps/web/tests/`；真正跨产品或跨共享包的组合验证，放在覆盖这些职责的共同上层测试目录。根级 `tests/` 仅在存在对应职责时创建，不默认集中收纳所有测试。
- Cargo 直接发现 crate 根 `tests/` 下的集成入口；更细职责目录由所属 crate 的测试入口或声明的 target 接入，不为目录规整增加无意义 crate。其他语言也由所属包的测试配置收集。
- fixture、golden、测试辅助代码和 benchmark 优先跟随被测模块；只有多个职责实际共用时才提取到共同上层，避免所有样本无差别堆到根目录。

现有 `src-tauri/tests/` 与前端相邻测试在迁移实现时按职责归位；本轮仅记录约定，不移动源码和测试。

### 2.3 已确认的能力边界与现有代码复用

采用“沿用现有成熟能力、逐步提取”的方式，以下是职责边界，不要求立即逐项创建独立 crate：

| 能力 | 现有代码来源 | 复用与调整 |
| --- | --- | --- |
| `model` | `edit/recipe.rs`、资产描述、events 中的领域类型 | 保留配方/参数/校验；去除 PhotoCraft 类型与默认值的直接依赖，以适配转换保持旧语义 |
| `media` | `edit/photocraft.rs`、masks、grading、parametric、source、GPU 处理 | 保留算法与处理顺序，集中 PhotoCraft 适配；拆来源/输出/呈现，增加 LibRaw 与胶片链 |
| `catalog` | db、资产/相册/图库 IPC 内的业务逻辑、编辑项目管理 | 保留业务规则，与 SQLite 实现分开；核心操作不从全局 AppState 查活动数据库 |
| `runtime` | tasks、index_budget、缩略图并发许可与缓存控制 | 复用取消/进度/错误隔离与许可机制，形成统一资源预算 |
| `protocol` | Rust DTO、`src/ipc/api/types.ts`、可公开事件载荷 | 保留业务含义，补网络身份/版本/结构化错误；不直接公开全部桌面 IPC |
| `sync` | 现有导入日志、校验和重试机制可参考 | 远程映射、游标、待提交操作、冲突和续传主要新增，不把本地导入冒充同步 |
| `ai` | ai 下推理与后处理 | 保留推理/人脸等算法，与资产读取、索引业务和宿主调度解耦 |
| `metadata` | EXIF/XMP/感知哈希等 metadata 代码 | 保留解析/编码与计算，来源和写入交给访问适配器 |
| `geo` | geo 下离线地理数据与查询 | 作为独立可选能力，按产品需要引用 |
| 存储适配 | db 的 SQL、文件缓存、资源落盘 | 保留 SQLite 本地实现；其他数据库/资源后端仅替换对应实现 |
| 导入能力 | import/engine 的复制、校验、查重和日志 | 保留流程，分离设备扫描、传输及资产登记 |

六个主干模块不是所有能力的上限。AI、元数据、地理、存储和导入保留独立职责，并按 §2.6 逐项提取为 crate；算法内部仍使用普通模块，后续新增能力按实际调用与依赖决定边界。

PhotoCraft 保持外部图像执行依赖，已有本项目适配迁入处理边界；不为重新分模块重写成熟滤镜。类型转换不改变默认值，迁移同一处理链不顺便改变操作顺序。

本地配方覆盖保存可以保留本地语义；服务端协作保存新增权限、revision 比较与事务，不直接复用普通 upsert 作为并发合同。

桌面设备/联拍/托盘留在桌面宿主，移动相册/生命周期/原生表面留在手机适配，认证/成员/工作区协作属于服务端。前端纯配方、坐标、历史和可复用调度逻辑进入 components；Tauri/窗口/系统访问留在 app，应用级 store 不整体迁入共享包。

按纵向流程迁移并运行原有职责测试，确认结果与行为后再扩大范围。库内部继续直接原生调用，逐像素循环不穿过仓储、网络协议或通用服务层。

### 2.4 已确认的 Rust 引用与构建模式

采用单一根 Cargo workspace，管理共享 crate 和各应用 Rust 入口，共用根 `Cargo.lock`。成员路径在具体 crate 和 app 布局确认后列明。

- 仓内通过 `path` 引用共享源码；共用依赖声明收敛到根 workspace。正常开发不复制代码、不使用子模块或先发布包再回接仓内消费者。
- 桌面、手机、服务端分别选择 package、目标 triple 和能力构建；每个产品有独立构建/发布入口。成为 workspace 成员不表示一次编译全部产品。
- GPU、AI、桌面设备等依赖按能力可选，平台专属依赖按目标条件声明。控制 Cargo feature 的加和行为；CI 分开验证各产品的实际 feature/target 组合，不将全 workspace/all-features 构建视为真实产品配置。
- 外部依赖使用版本/提交与锁文件保持可复现，重点统一 PhotoCraft、LibRaw 与 GPU 依赖。C/C++ 库针对实际目标编译，不能混用宿主库；源码/产物存放和构建缓存细节后续讨论。
- 共享算法和同机处理使用原生直接调用；C ABI 明确缓冲所有权与生命周期，避免逐像素跨语言调用。远程服务使用网络协议，持久后台任务需要时可交给 worker，这不改变库内热路径。
- 编译产物可以由 Cargo/构建缓存复用，但不依赖另一产品已经生成的临时文件或私有构建目录。离线/CI 从固定输入可重建。
- 根 workspace 和锁文件迁移作为单独实施步骤；现有桌面构建脚本、缓存、CI 路径与测试入口同时调整并验证，文档阶段不移动当前工程。

### 2.5 已确认的 TypeScript 共享组件引用方式

采用 A：应用直接消费 `components/` 下共享组件的 TypeScript 源码，由应用构建工具编译和打包。仓内使用不以共享组件先生成 dist 为前提。

- 每个实际共享组件有独立 `package.json` 和公开导出入口；应用通过包名引用，如 `@photographer/editor-model`（具体组件名后续确定）。
- 不通过跨目录相对路径绕过入口导入另一组件内部文件；组件之间的依赖也显式声明。
- 共享组件不依赖具体 app；Tauri、浏览器 HTTP、窗口与系统能力通过应用适配器接入。
- 单测、集成测试和类型检查由组件按职责管理，应用的集成/构建验证其源码在消费者环境中的兼容性。
- 需要仓外发布时再为对应组件增加 JS/类型声明产物；不让所有仓内开发都先经过发布流程。
- 前端包管理工具、workspace 配置和依赖版本策略继续讨论；本决定只固定源码消费和公开入口约束。

### 2.6 已确认的 Rust crate 粒度

采用 A：按能力拆 crate，逐个提取，有实际实现时才创建，不预先建立空包。目录规划为：

```text
crates/
├── model/
├── media/
├── catalog/
├── runtime/
├── protocol/
├── sync/
├── ai/
├── metadata/
├── geo/
├── storage-sqlite/
└── import/
```

这些包承接 §2.3 的现有代码与职责。media 内的曝光、曲线、LUT 等仍为普通模块和直接函数调用，不按每个算法拆包。重型原生/GPU/推理依赖分别归属 media、ai 等实际使用者，纯模型与协议消费者不被迫加载它们。

允许依赖按 §2.7；crate 的公开入口、repository/来源接口签名和 Cargo 包名在实施对应模块时细化。本决定不表示上述目录已经创建或代码已移动。

### 2.7 已确认的依赖方向

箭头表示依赖，以下为架构允许方向，实际代码只声明所需依赖，不因表中允许就提前引入所有包：

```text
media          → model、runtime、metadata
ai             → model、runtime
metadata       → model
geo            → model
catalog        → model
protocol       → model
sync           → model、protocol、runtime
import         → model、catalog、metadata、runtime
storage-sqlite → catalog 等使用方定义的仓储接口
apps           → 按需装配上述能力与平台实现
```

- model 保持纯类型/校验等轻量能力，不依赖 PhotoCraft、数据库、GPU 或网络；runtime 不知道相册、用户和具体业务。
- 算法通过明确的数据衔接，例如 app 调用 media 解码，再将借用的图像视图交给 ai；不要求 ai 引入完整图像解码引擎或复制整幅像素。
- 仓储接口由使用方定义、具体存储实现依赖接口。例如 catalog 定义资产仓储接口，storage-sqlite 实现；其他数据库实现保持同一业务合同。具体事务边界与接口签名后续确定。
- “导入、元数据、登记、缩略图、AI”等跨能力编排由应用服务按产品需求装配，直接使用原生调用。共享算法不反向依赖应用服务，不能形成 media/catalog 等循环。
- 允许接口扩展时补充独立能力，但要同时审查依赖方向与实际调用；不得把不相关的宿主或存储实现塞入 model 以绕过依赖规则。

## 3. 复用到什么程度

- **强复用：** 配方语义、参数范围、色彩/Log 数学、胶片/LUT、空间尺度约定、几何/蒙版坐标、错误类型、CPU 参考与数值样本。
- **条件复用：** PhotoCraft 渲染准备与合成、LibRaw、编解码、AI 推理、缓存策略和任务状态机；按产品需要链接，浏览器无需编译/加载这些原生图像组件。
- **合同复用、实现分开：** 资产读取、存储、repository、任务执行、GPU 呈现、输出目标和网络传输。只有出现实际不同实现时才增加 trait，优先具体类型与小接口。
- **产品独立：** 服务端登录/成员/协作、系统相册、后台执行资格、桌面设备、浏览器资源交付、服务器部署与各产品 UI。桌面/手机共用远程同步合同与逻辑，但各自控制调度和资源预算；本地核心不要求 Actor/Workspace 权限上下文。

核心不强制包含一个万能 AppState，也不强制所有消费者都使用 SQLite/Tauri。用户权限在服务入口与业务服务执行，图像数学函数不接收 user_id。需要权限的操作先得到已授权、已固定来源版本的数据访问租约，再进入图像处理。

## 4. 在已有八个抽象上的调整

| 原边界 | 为 Web/多用户新增的合同 |
| --- | --- |
| A：资产读取 | 增加服务器受管理文件/对象存储；客户端只持资源 ID，服务端内部解析存储地址；访问必须绑定工作区与授权 |
| B：存储与缓存 | 工作区隔离、授权资源交付、数据库实现可替换；缓存键包含工作区/来源版本/权限相关维度 |
| C：显影与色彩 | 服务端复用原生算法做异步预览/成片，桌面本机处理远程已授权数据；浏览器只接收编码结果 |
| D：会话与呈现 | 渲染执行、结果交付、终端呈现三层；本机实时会话与浏览器异步任务不是同一个生命周期 |
| E：任务/生命周期 | 服务端持久队列、worker 租约/恢复、浏览器断线；任务生命不等于 HTTP 连接生命 |
| F：资源预算 | 服务端全局预算加用户/工作区公平配额，浏览/异步预览优先，批量导出/AI 排队；本地仍是单用户预算 |
| G：导出目标 | 服务端结果资源、授权下载、分享/共享图库；浏览器本地保存由浏览器完成，不能将本地文件夹路径传给服务器 |
| H：宿主装配 | 拆为桌面、手机、服务器三种入口；共享业务服务不依赖 Tauri，网络端只开放受控业务接口 |

额外建立四项边界：**远程传输、服务端 Actor/Workspace 授权上下文、带 revision 的协作写入、本地客户端同步**。服务端授权和并发必须从服务原型开始存在；通过适配器与本地隔离，不能给所有本地函数强制添加 user_id。

## 5. 客户端传输与资源交付

当前 `src/ipc/index.ts` 直接调用 Tauri invoke，`api/events.ts` 使用全局 app 事件；缩略图/地图等返回本地路径并依赖 convertFileSrc。需要整理为：

- `ClientTransport`：业务请求、结构化错误、二进制下载、事件订阅和连接恢复。保留现有类型化域 API，不让页面各自判断 Tauri/浏览器。
- 本地适配器使用 invoke/应用事件；远程适配器使用 HTTP 与 SSE/WebSocket。网络 API 有独立路由与校验，不把任意 Tauri 命令字符串映射成公开 RPC。
- `ResourceHandle` 区分本地受控资源、Blob、受授权 URL、原生纹理；前端不要求服务器响应本地绝对路径。
- 远程请求含协议版本、request_id、目标 workspace_id 以及需要的资源/revision。身份来自服务端验证的会话，客户端提供的工作区只是选择器。本地请求继续走单用户服务，不伪造远程登录上下文。
- 错误明确区分不可达、未登录、无权限、源不可用、版本冲突、资源不足、任务失败；当前字符串正则判断 invoke 可用性不能承担网络错误模型。
- 上传、导出等重试操作使用幂等键；查询与操作错误不能永久把整个应用标记离线。
- 事件按已授权工作区/资源/任务订阅。断线后按序号补事件或重新取快照，不能向所有客户端广播全局 EventBus。

媒体内容通过授权资源端点交付，支持需要的范围读取、版本标记与缓存；访问权限变化后停止订阅并失效后续访问。不能将服务器任意路径、数据库目录和全部缓存目录暴露为静态站点。浏览器 File 通过上传协议进入服务端，上传完成/校验后才登记资产。

## 6. 浏览器受限编辑与本地客户端远程编辑

浏览器只提供管理/协作所需的图像浏览和异步高级编辑，不要求实时 GPU 编辑、浏览器 LibRaw、WASM PhotoCraft 或逐帧网络图像推送。

```text
浏览器：照片管理 / 协作 / 配方调整
                  ↓ 提交预览或导出任务
服务端：固定源版本 + 固定配方 → 无头渲染 → 编码结果资源
                  ↓ 任务状态 / 授权 URL
浏览器：显示预览、版本对比、下载成片

桌面/手机远程客户端：授权资源下载 → 本机实时编辑
                             ↓ 配方/元数据变更同步
服务端：校验权限与 revision → 保存共享版本 / 异步导出
```

- 浏览器预览采用提交/防抖任务，返回 job_id 与进度，完成后更新画面；旧任务结果不能覆盖新配方，队列有界，不按滑块每帧写共享历史。
- 高级配方格式和服务端渲染保持桌面语义；浏览器暂不提供的复杂操作要完整保留字段，不能因为面板受限而覆盖丢失蒙版/图层参数。
- 浏览器显示编码后的 JPEG/PNG 等结果，sRGB 为基线，不下载线性 float 代理来执行本地实时算法。
- 桌面/手机远程客户端可缓存高精度代理/原图，使用本机原生处理与 GPU；下载合同包含源版本、色彩、编码、方向和尺度。仅有显示缩略图时不能宣称具备完整 RAW 编辑质量，手机按内存/网络预算选择下载层级。
- 服务端负责完整 RAW 与最终输出，本地客户端也可在获准下载完整原图后本机导出；两者按能力与权限选择，不将两条结果混为已同步状态。
- 事件连接只发送任务、版本和管理通知；无需实时帧流。若选 WebSocket，仍应限制队列与处理断线，参考 [MDN WebSocket](https://developer.mozilla.org/en-US/docs/Web/API/WebSocket)。

桌面/手机实时性能目标继续沿用本地计划；Web 验收改为任务反馈、正确预览、并发公平和服务恢复，不要求 30 fps 或输入到画面 100 ms。

## 7. 用户、工作区与请求上下文

当前 `AppState.settings.active_database_id` 是进程全局选择；多用户服务不能让 A 的切库影响 B。当前配方按 asset_id 覆盖保存、LUT 根目录为进程级 OnceLock、预览会话为全局 map，这些都是明确迁移点。

建议领域对象：

- `Actor`：用户/服务身份，由可信宿主或服务器认证建立。
- `Workspace`：个人或共享工作区，拥有资源、相册、方案和任务；不是一名用户独占一份业务数据的同义词。
- `Membership`：工作区成员及角色；首期 owner/admin/editor/viewer，细粒度分享后续扩展。
- `RequestContext`：actor、经授权的 workspace、request_id、取消/截止时间；参数不由前端自报身份赋权。
- 机器级设置、工作区处理设置、个人偏好分层；用户默认活动工作区只是偏好，执行操作时显式携带已验证范围。

这些对象只属于服务端业务/远程协议。本地产品继续单用户数据库与设置，不为本地模式增加成员、角色和协作权限。桌面/手机远程适配器持有登录及工作区选择，远程调用绑定服务端上下文；本地工作台不因连接、退出或切换服务器而换库或改变数据归属。

认证/会话放服务宿主；权限检查在实际业务操作与数据查询边界执行，覆盖原图、缩略图、代理、LUT、AI 搜索、人脸索引、导出和任务事件。SQLite 文件分开或 UUID 难猜都不能代替授权。参考 [OWASP Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)。

## 8. 协作编辑与版本冲突

首期采取“共享工作区 + 独立编辑版本 + 乐观并发”的方式，不实现通用 CRDT：

- 从“每资产一份配方”演进为 `EditDocument`：所属工作区、资产 ID、编辑版本 ID、作者、revision、配方/渲染合同及更新时间。
- 私人草稿、共享已发布版本分开；多人可以为同一原图建立不同版本，共享基础资产，不互相覆盖。
- 保存携带 expected_revision；数据库在事务中比较并更新，冲突返回当前 revision，拒绝最后写入静默覆盖。读取后再普通 upsert 不满足并发合同。
- 共享版本发布、恢复旧版本和导出产生可追踪记录；作者、时间、前后 revision 可查。
- 预览会话绑定 actor/workspace/编辑版本和快照，不直接修改共享持久配方；每次拖动只更新私有临时预览，不把高频帧全部记审计日志。
- 用户明确保存/发布后广播版本变更；在线 presence/编辑提示可加租约，但锁提示不是数据库并发正确性的保证。
- 后续确需同文档实时共编时，再定义参数、曲线点、图层、蒙版笔迹的操作模型与合并规则。整份 JSON last-write-wins 不能实现可靠实时协作。

评分、标签、评论等也需区分个人信息与共享信息。现有人脸命名/聚类、AI 索引的共享范围由工作区权限确定，不能无意跨用户搜索。

## 9. 数据存储与仓储实现

定义按业务用例拆分的 repository 合同，如资产查询、编辑文档 CAS 保存、成员关系、任务领取/完成；不做一个万能数据库 trait，也不强迫服务端复刻所有桌面 Db 方法。

- 桌面/手机继续 SQLite；本地业务保留当前实现，经服务边界调用。
- 单节点、低写入并发的服务原型可使用 SQLite，工作区作为作用域；不把数据库文件放网络共享目录供客户端直接打开。
- 有持续多人写入或多服务实例需求时，建议服务版 PostgreSQL；事务、约束和 CAS 行为保持合同一致，不按用户名拆出互不相通的个人库来实现共享协作。
- 原图与代理由 BlobStore/AssetAccess 管理，首期受管理本地磁盘，后续对象存储；数据库只保存标识、版本和必要元信息，不向客户端泄露内部地址。
- 向量索引、LUT 资源、缓存、任务和预览会话按工作区隔离；内容哈希相同可以内部复用，但访问授权仍独立。
- 当前未发布单版本 schema 约定继续有效，不在本轮创建历史迁移框架。长期服务版发布后需要明确的升级/备份机制，届时以服务版的发布契约设计，不能靠启动 IF NOT EXISTS 完成结构升级。

SQLite 支持服务端网站用途，并不因为多用户自动不可用；高写入并发/多服务器时需考虑客户端服务器数据库。这些边界见 [SQLite 适用场景](https://www.sqlite.org/whentouse.html)。PostgreSQL 是针对本项目后续协作目标的建议，不是已完成的替换决定。

## 10. 本地客户端同步：RemoteConnection / SyncJournal / ReplicaStore

服务器可作为桌面/手机照片管理与协作的同步服务；不是简单上传整个 SQLite 或镜像照片目录。协议、待提交日志和冲突状态尽量复用，手机生命周期/传输预算通过策略适配。

- `RemoteConnection` 管理服务器身份、账号会话、工作区和能力；本地数据库、服务器连接及远程工作区互相独立，不复用本地 active_database_id 作为远程全局状态。
- 远程资产/编辑版本使用稳定服务标识。本地 asset_id 只是本地数据库键；映射按 server/workspace/resource 保存，不能假定两端整数 ID 相同。
- 同步对象优先为照片元数据、评分/标签、相册关系、编辑配方/版本、LUT 引用和结果资源。原图按选择上传/下载，缩略图与高精度代理可按需拉取；不默认全量复制全部照片。
- 默认不同步绝对路径、GPU 缓存、进程会话、当前视口、完整撤销栈、模型文件或本机设备设置。共享元数据与个人草稿明确区分。
- `SyncJournal` 保存本地待提交操作、operation_id、base_revision 和资源依赖；断网后可继续已缓存内容的本机编辑，重连后按幂等键提交。离线操作的可用性取决于已下载资源。
- 服务端提供按工作区递增的变更游标、快照和删除标记；初次同步取快照，再按游标拉取。游标过期执行重新对账，不靠修改时间戳判断冲突。
- 共享配方变更使用 expected_revision；冲突不静默 last-write-wins。首期保留本地草稿并提示另存编辑版本/重新基于服务版本提交，不引入自动合并复杂蒙版。
- 原图内容以版本/哈希核实，上传支持断点与临时提交；完成校验后登记，配方引用的 LUT 资源到齐后才接受对应版本。
- 删除共享记录、撤回权限、删除本地缓存和删除受管理原图分别处理。服务端删除使用 tombstone/回收策略，首期不自动永久删除独立本地原图。
- 恢复连接后重新校验身份与权限；服务器状态是共享协作权威，本地 journal 是待提交工作，不把两者伪装成相同 revision。

手机与桌面一样具备接入协作的架构位置。手机进入后台可以暂停传输，恢复后沿用 journal 与游标续做；后台任务资格不改变同步正确性。是否提供批量原图下载、复杂编辑或全部管理功能等留待功能裁剪讨论，不能因此把服务端多人协作权威塞进本地业务。

## 11. 服务任务、资源公平与隔离

- 持久任务包含 actor/workspace、源版本、冻结配方、资源版本、幂等键、状态和结果 ID。请求断开后导出继续，临时预览按会话 TTL 清理。
- 首期单服务可内嵌 worker；领取使用事务和租约，worker 崩溃后可恢复，提交去重。后续 worker 独立进程不用改变用户 API。
- 按全局、工作区、用户分配 RAW/AI/GPU、缓存和导出并发预算；一个用户批量处理不能饿死另一人的预览。
- 长任务执行、结果提交/下载时核实授权策略；成员撤权后不得继续订阅或下载结果。任务与权限变化的处理要一致，不能只在创建任务时检查。
- Linux 无 GPU 也能完成工作；有 GPU 时走无头计算，不依赖桌面会话、DISPLAY 或 swapchain。GPU 后端/模型加速独立验证。
- 对原生解码的失败与超时，后续评估独立 worker 进程；线程 panic 捕获不能隔离 C++ 崩溃/OOM。原生重计算结束前仍计入预算。

## 12. 前期实施顺序（供追溯）

下列 S0–S6 为讨论阶段安排，已由 [统一实施顺序 M0–M8](platform-evolution/implementation.md) 取代；不继续在本节更新执行状态。

| 阶段 | 工作与出口 |
| --- | --- |
| S0：合同/原型 | 固定本地/远程/浏览器边界，具体功能后续讨论；验证 Linux 无头 CPU 处理、异步高级编辑和本地客户端远程资源打开；记录依赖、内存与色彩合同 |
| S1：共享核心边界 | 核心服务不依赖 Tauri；建立 AssetAccess、WorkingImage、版本化配方与目标提交；桌面保持可用，假来源/假目标通过 |
| S2：服务上下文与远程传输 | 服务端 Actor/Workspace、桌面/手机共用的远程适配合同、HTTP/事件、资源句柄与结构化错误；本地业务不依赖协作权限，全局活动数据库不进入服务请求 |
| S3：最小 Linux Web 服务 | 认证和工作区授权，上传→图库/相册管理→异步高级编辑→导出下载；不公开设备命令或任意路径访问 |
| S4：协作、同步与恢复 | 成员角色、独立编辑版本、事务 CAS、授权事件、任务租约和公平预算；共用 journal/变更游标、断线重连、资源依赖和冲突处理，先在桌面验证 |
| S5：共享包与手机适配 | 在同仓建立经桌面/Web 消费者验证的共享包；手机复用本地核心及远程同步组件，接 Android/iOS 原生来源/呈现/生命周期并验证协作连接，桌面 OS 仍共用产品 |
| S6：扩展 | 服务 PostgreSQL/对象存储/独立 worker、AI、在线 presence；具体各端功能裁剪及同文档实时共编按后续需求评估 |

S0 的手机最小构建也应提前开展，尽早发现 LibRaw/编解码等原生依赖边界。与原移动计划 P0–P4 共用资产、资源、显影和导出任务；原 P5 的手机完整适配在 S5 进行，避免按两份计划重复重构。

共享核心提取之前必须出现真实的第二个消费者，避免根据想象把所有平台差异都做成接口。首期不要求部署微服务、消息中间件或浏览器完整 RAW 解码。

## 13. 验收与风险

- 两用户同时切换工作区、编辑、导出、上传，不污染对方上下文；猜测 session/asset/job/resource ID 不越权。
- 修改角色/撤权后，媒体访问、任务查询、事件订阅和向量搜索同步遵守范围。
- 同一编辑版本并发保存只有符合 expected_revision 的操作成功，冲突可见；同一原图多编辑版本可独立保存和导出。
- 浏览器异步任务状态可恢复，旧预览不覆盖新配方；桌面本机实时处理与服务端渲染按共享色彩合同对照，不要求浏览器本地渲染。
- 桌面/手机离线修改、重复推送、游标过期、跨服务器/工作区 ID 重复及服务端删除正确处理；本地模式不依赖登录、不自动变成共享库；手机挂起/恢复后可续传。
- 上传中断、服务重启、worker 失效和重复提交不重复登记/产出；导出只使用冻结配方与固定源版本。
- Linux 无 GUI、无 GPU 的最小服务镜像完成整个核心流程；有 GPU 只作为额外加速能力。
- 三种产品共享配方/胶片/坐标语义；浏览器功能限制明确且保留未编辑字段，服务端可渲染本地客户端共享版本；桌面/手机连接服务时复用同一权限与协作合同。
- 同仓共享包的受影响消费者 CI 可复现，各产品独立构建发布，升级不会自动改旧配方效果。

工作量在 S0 后重新评估。不再估算浏览器实时 GPU/WASM 图像引擎；服务传输、认证/工作区、CAS 协作、本地客户端增量同步和资源交付仍超出原手机抽象范围。先完成单节点、小规模多用户及桌面连接的纵向流程，再接手机与实际并发扩展；具体功能裁剪确定后再承诺产品工期。
