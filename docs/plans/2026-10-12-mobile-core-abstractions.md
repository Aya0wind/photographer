# Android/iOS 共用核心的抽象与迁移计划

日期：2026-10-12。状态：待实施；本次仅制定计划，不代表移动端已经可编译或运行。

本文件保留前期移动端抽象讨论。当前工程组织、模块归属、实施顺序和验收已拆分至 [多形态应用与共享核心实施方案](platform-evolution/README.md)，后续执行与状态更新以新目录为准。

补充范围：同时考虑 Linux Web 服务、多用户协作及按桌面/手机/Web 三种产品形态独立实现，见 [共用核心与 Web 协作计划](2026-10-12-shared-core-web-collaboration.md)。按产品形态划分，不按操作系统拆产品；该计划补充传输、授权上下文和版本冲突，并调整后续提取与适配顺序。

本地桌面/手机继续单用户，不要求本地模式实现多人协作或登录。二者都可以作为远程客户端连接服务器，由服务端执行权限/协作并提供同步；远程协议、同步 journal 和冲突处理尽量共用，手机生命周期与资源预算独立适配。本地核心不强制引入服务端 Actor/Workspace，具体各端功能裁剪后续讨论。

## 1. 范围与原则

目标是保留图库、编辑配方、实时调色、LUT/胶片、局部蒙版、预览和导出等手机需要的能力，使桌面、Android、iOS 复用同一业务与色彩核心。UI 改版、桌面专属功能移植不在本计划范围；不需要的功能仍须从移动构建和启动装配中排除。

与 [LibRaw 显影、Smart Preview 与胶片模拟计划](2026-10-12-libraw-smart-preview-film.md) 联合实施：先快速 JPEG 编辑，后台生成线性 RAW 代理，候选帧应用最新配方后切换，导出处理完整 RAW。后台生成不意味着应用进入系统后台后仍保证持续运行。

优先在当前 Rust 模块内形成可测试边界，不首先拆成大量 crate，不引入包含文件、GPU、任务和权限的万能平台 trait。只抽象会变化的宿主能力；PhotoCraft 数学算法、蒙版、SQLite 业务和配方不因移动端而重写。

先完成桌面适配器与契约测试，再接 Android/iOS；桌面每个阶段仍能正常编辑。本文中的接口名是建议职责名，最终签名在实现时由现有调用与最小原型确定。

## 2. 当前边界与可复用实现

| 现有位置 | 可以保留 | 需要改变的假设 |
| --- | --- | --- |
| `devices::DeviceSource` | 枚举、流式读取、设备预览、已有本地/设备源实现 | 服务于导入设备，不等于图库资产访问；不要求移动资产实现设备发现/删除 |
| `platform::ResourceRef` | 区分本地路径和 URI 的基本语义 | 只有借用字符串且 URI 访问未实现，不含授权、版本、租约或系统照片身份 |
| `db/schema.rs`、`db/libraries.rs` | SQLite、图库关系、相册、评分、分组 | 照片库等同文件夹，资产 `path` 唯一；不能代表系统相册资产和授权文档 |
| `edit/source.rs` | 文档转换、现有 PhotoCraft 后端 | 解码与显影输入依赖本地路径，没有明确区分来源、图像编码和显影后端 |
| `edit/preview.rs`、`proxy_cache.rs` | 最新请求、会话、代理复用与损坏重建 | 会话/缓存以路径、mtime、大小识别来源，固定 JPEG 代理与全局状态 |
| `preview_renderer.rs`、`gpu.rs`、`native_presenter.rs` | 调整层更新、GPU 合成、缓存、显示转换 | 文档准备、执行和显示边界不完整；直接纹理呈现只有 Windows 实现 |
| `tasks/mod.rs`、`tasks/index_budget.rs` | 错误隔离、软暂停取消、索引预算 | 线程句柄和进程内状态不能承担系统挂起、进程重建与任务恢复 |
| `edit/export.rs`、`edit/project.rs` | 配方冻结、编码、元数据、归属校验 | 输出主要是文件夹/本地相册；核心入口依赖 AppState 和 Tauri State |
| `ai`、`platform::InferencePlan` | 索引业务、推理选择、失败回退 | 手机运行库、模型驻留、温度/电量预算尚未接入 |
| `lib.rs`、`Cargo.toml`、Tauri 配置 | Rust/Tauri 入口与桌面实现 | 服务、插件与资源默认按桌面装配；Android 占位，iOS 通用回退 |

## 3. 必须重新建立的八个边界

### A. 资产身份与读取：AssetLocator / AssetAccess

**位置：** `platform/mod.rs`、`devices/mod.rs`、`db`、`thumbs`、`metadata`、`edit/source.rs`、AI 图像读取。

- 资产身份由数据库身份加资产 ID 定位；来源描述可表示受管理文件、外部本地路径、Android 文档/媒体 URI、iOS Photos 资产与授权文档。
- 身份、显示名称、授权信息、源版本和访问状态分别表达，不使用临时下载路径代替持久化身份。
- 能力包括元信息查询、预览请求、可取消读取及按需物化为可寻址本地文件；仅在消费者确实需要时提供 seek 或本地文件。
- 返回访问租约，明确授权、文件描述符、临时文件和缓冲的释放；不能强迫具有主线程约束的原生对象实现无条件 Send/Sync。
- 区分可用、需授权、权限撤回、云端待下载、源版本变化、不支持和文件损坏，不统一降级成“文件不存在”。
- 复用 DeviceSource 的本地/流式传输实现，但保留其导入职责；不把删除、设备枚举强行塞给所有图库来源。
- 图库、缩略图、元数据、编辑和 AI 逐步改用同一读取入口，缓存键改用资产身份加源版本。

首期手机采用复制到受管理存储的方式导入原图，系统选择/授权仍经原生适配完成。外部长期引用和云端按需访问作为扩展，接口应预留但不一次实现所有提供者。

### B. 持久数据、来源与缓存：StorageLayout / AssetRepository / CacheStore

**位置：** `settings`、`ipc::app_database_dir`、`db/schema.rs`、`db/libraries.rs`、`edit/proxy_cache.rs`、`thumbs`、模型/索引目录。

- 区分数据库/配方等必须持久保存的数据、受管理原图、可清理代理/缩略图、可重新下载模型，以及长期访问凭据。
- 来源提供者与用户照片库分开建模；桌面文件夹作为一种来源，不把系统相册伪装成根目录。
- 缓存提供租约、原子提交、校验、按字节预算和淘汰；正在使用的数据不可被删。缓存被系统清理后可重建。
- 文件路径只存在于来源/存储适配器及确实需要本地文件的库边界；业务代码不能拼接 URI，不能使用 inode/mtime 作为所有来源的版本合同。
- SQLite 和既有 repository 方法继续保留；先调整输入/来源字段，再修改调用方，不增加与 SQLite 并行的第二套业务存储。
- 当前 `db/schema.rs` 明确采用未发布单版本 schema、不引入历史迁移框架；本计划遵守该约定。实施时更新最终 schema 和初始化检查，不自行添加通用 migrate 系统。不得静默损坏现有用户数据；旧数据处理按届时实际发布状态和项目约定确定。

### C. 解码、显影与色彩交接：ImageSource / RawDeveloper / WorkingImage

**位置：** `edit/source.rs`、`photocraft.rs`、LibRaw C ABI 接入、查看器完整 RAW 路径。

- 来源访问与解码分开；RAW 后端接收授权读取结果，不直接依赖 Tauri、AppState 或系统照片 API。
- 区分快速 JPEG、线性 RAW 代理和完整质量显影三种意图，明确尺寸、方向、原始坐标映射、质量、取消与内存估算。
- 工作图像显式携带 primaries/白点、传递函数、像素格式、步幅、方向和曝光基准；裸 Vec 或“RGB”字符串不足以描述颜色。
- LibRaw 与当前 PhotoCraft 显影放在明确的后端适配中，旧配方解释不随运行平台改变。
- 胶片色域/Log/LUT、强度混合形成共用阶段，CPU 参考与 GPU 实现共用数学/版本合同；禁止在不同宿主重复发明处理顺序。
- 相机绝对白平衡、代理上的相对反馈、曝光基准与用户 EV 分开记录，按 RAW 计划验证精确更新，不重复作用。
- C ABI 采用清楚的会话/缓冲所有权、错误返回和版本；Android/iOS 按目标 ABI/SDK 构建，不能加载宿主桌面库。

### D. 编辑会话、GPU 执行与呈现：EditorSession / RenderExecutor / Presenter

**位置：** `preview.rs`、`preview_renderer.rs`、`native_canvas.rs`、`native_presenter.rs`、`gpu.rs`、前端预览调度。

- 编辑会话管理资产快照、配方 revision、source revision、来源状态和阶段缓存，不管理窗口句柄。
- 渲染执行器负责 CPU/GPU 处理与中间结果；呈现器负责原生表面、尺寸和实际呈现。原生纹理结果不是必经 CPU 字节数组。
- Windows 原生呈现、WebView 回退、Android Surface、iOS Metal 呈现分别适配；可以使用不同平台 API，业务层不依赖 HWND/UIView/JNI 对象。
- GPU 结果保留线程与设备归属，避免为了跨平台抽象而强迫跨线程搬运纹理。IPC 只传配方、视口和版本，图片通过受控资源通道提供。
- 代理就绪后先渲染当前最新配方，确认 revision 后原子切换；保留视口、工具、历史和原始坐标蒙版。
- 表面销毁、GPU 丢失、应用挂起后可释放 GPU 资源并重建；图像与配方不是随表面消失的临时状态。
- 取色、直方图、剪切、对比画面跟随当前 source revision；诊断分别记录准备完成和真实呈现时间。

### E. 生命周期与可恢复任务：LifecyclePolicy / TaskRecord / Scheduler

**位置：** `tasks`、`lib.rs`、`events`、导入/索引/导出 worker、编辑会话保存。

- 将应用前台、后台、恢复、内存压力等宿主事件转换为核心执行策略；移动系统后台资格由原生适配提供，不由普通 Rust 线程推定。
- 保留 TaskSupervisor 作为执行和错误隔离机制；持久任务记录与当前线程句柄分开。
- 导入/导出记录任务 ID、冻结配方、资产/资源版本、阶段、输出提交状态及可恢复信息。任务幂等，恢复不重复入册或覆盖另一张成片。
- 复用既有导入日志和索引 pending 状态，不额外制造独立的恢复真值。预览帧、GPU 缓存及可重建代理无需逐帧持久化。
- 活跃编辑配方按 revision 防乱序写入；后台前尽量保存，仍需常规增量保存，因为进程被杀不保证收到回调。持久化当前配方，不把完整撤销栈保存设为首期前提。
- 前端重新连接后按快照/任务状态恢复；事件是通知，不是唯一真值。不能依赖每条历史事件都送达。
- 取消与超时明确区分“调用已停止”和“仅丢弃结果”；不支持中断的 LibRaw/滤镜调用继续计入资源预算直到退出。

### F. 统一计算与内存预算：ResourcePolicy

**位置：** `thumbs::desired_permits`、`tasks::index_parallelism`、`index_budget`、GPU/代理缓存、RAW 和 AI。

- 在现有 permit/索引预算上统一前台优先级、任务并发和预计峰值字节；先提供小而具体的策略与许可，不重新发明通用调度框架。
- 策略输入包括平台档位、可用内存、前后台、温度/电量状态及当前前台交互；无法获取某项时采取明确的保守默认值。
- 手机默认单个重 RAW 任务；代理、导出和 AI 不能各自独立抢占全部核心/内存。
- 分别核算传感器、中间 float、文档瓦片、CPU 缓存、GPU 和读回数据；不能只按代理输出尺寸估算 LibRaw 峰值。
- 预览尺寸和质量由策略给定；缓存实现负责按字节淘汰，处理算法不直接调用 num_cpus 决定全局资源占用。

### G. 导出编码与目标提交：ExportRenderer / ExportDestination

**位置：** `edit/export.rs`、`photocraft.rs`、`meta.rs`、导出登记和 IPC DTO。

- 共用渲染/编码产生临时成片，目标适配负责本地目录、受管理图库、系统相册、授权文档或分享。
- 定义 prepare/write/commit/abort 职责与提交回执；记录实际目标资产身份，不假定输出总能返回文件绝对路径。
- 本地目标沿用临时文件及 rename 语义；系统相册/远端文档使用各自提交规则，不假定都支持原子 rename。
- 恢复先查询已提交回执；提交成功、数据库登记失败与编码失败分别处理，避免重试产生重复照片。
- 来源只读授权与写入/删除授权分开。删除应用记录、删除受管理副本与删除系统原图分别建模。
- XMP/EXIF 的编辑意图保留在配方/数据库；没有原图写权限时不强行改原文件或旁边写 sidecar，导出时应用元数据。

### H. 宿主装配与能力快照：CoreServices / HostCapabilities

**位置：** `lib.rs`、`ipc/mod.rs`、`platform`、Cargo feature/目标依赖、Tauri 配置与权限。

- IPC 保留为薄壳：将 State/AppHandle 转为核心服务输入；编辑、资产、任务、导出核心不直接依赖窗口或 Tauri State。
- 在当前模块内按服务整理 AppState，渐进减少跨模块取全局状态；先只拆有实际迁移需求的接口，不强制每个函数都变 trait。
- 扩展既有 PlatformCapabilities：来源访问、RAW 后端、GPU 渲染/呈现、可恢复后台任务、输出目标和可选 AI。编译支持、运行可用、用户授权分别表达。
- 桌面专属插件、依赖、资源和常驻服务按 cfg/feature 隔离；Android/iOS 有独立装配入口和原生桥接。
- 若保留 AI，扩展现有 InferencePlan/模型加载入口，验证移动运行库及模型预算，不为手机重写人脸/索引业务。
- 构建依赖审计覆盖 LibRaw、turbojpeg、ONNX Runtime、usearch 等原生组件；暂不需要的能力从移动构建排除，不能仅隐藏 UI。

## 4. 前期实施顺序与阶段出口（供追溯）

下列 P0–P6 保留移动端讨论过程；当前执行顺序与状态改用 [统一实施顺序 M0–M8](platform-evolution/implementation.md) 和 [roadmap](platform-evolution/roadmap.md)。下文工期与下一步建议属于前期局部评估，不作为三端整体排期。

| 阶段 | 工作 | 必须交付的结果 |
| --- | --- | --- |
| P0：合同与基线 | 核对路径调用、source/version、色彩、资源峰值和旧配方；明确手机首期功能 | 桌面行为基线、接口合同、依赖可构建清单、代表 RAW/图片样本 |
| P1：资产与存储 | A/B；先桌面本地实现，再内存/无路径假源，最后手机导入副本 | 无路径来源可完成缩略图、元数据与编辑打开；数据库身份/权限/缓存失效一致 |
| P2：核心服务与资源策略 | H 的服务边界、E/F 的保存和预算；连接生命周期假源 | 核心测试不需要窗口；挂起/恢复不丢配方；重任务受同一预算约束 |
| P3：显影与预览 | C/D，接 LibRaw 和线性代理，先 Windows 保持现有画布 | JPEG → RAW 代理切换不丢编辑；LUT/胶片实时更新；颜色和坐标合同通过 |
| P4：导出与恢复 | G，补 E 的导出记录与恢复 | 同一配方完整 RAW 输出；提交重试不重复入册；无本地路径目标可用 |
| P5：Android/iOS 适配 | 原生来源/权限、GPU 表面、生命周期、输出、目标库构建 | 各平台真机完成打开、编辑、切后台/回来、导出、权限撤回和内存压力验证 |
| P6：可选能力 | AI、外部长期引用、云端读取、高分辨率区域代理 | 独立性能/内存/恢复证据，不阻塞首期核心摄影流程 |

依赖关系：P1 → P2 → P3 → P4 → P5。P0 的移动最小构建与表面原型应尽早做，发现依赖不可构建或纹理无法呈现时立即反馈，不等到所有桌面抽象完成后才试手机。P3 与既有 LibRaw 计划共用任务，不重复安排两次工程。

每阶段以一个可用的纵向流程迁移，不一次替换全部路径调用。完成桌面实现与契约验证后再移除对应旧入口；未完成的功能保留兼容适配，不通过空实现伪装支持。

## 5. 验证要求

- 资产：无本地路径、权限撤回、云端延迟、源版本变更、授权租约释放、临时文件清理、数据库切换身份隔离。
- 存储：系统清缓存可重建，原图/配方不随缓存删除；正在读取的代理不被淘汰；损坏缓存原子恢复。
- 会话：调色中代理完成、快速切图、过期帧、视口保留、GPU 表面重建、直方图/取色来源一致。
- 任务：中断后从检查点恢复、未收到退出回调、事件遗漏、取消不支持中断的算法、暂停期间资源计数不失真。
- 导出：CPU/GPU、代理/完整 RAW 的色彩与尺度语义，失败提交、重复重试、登记失败、权限撤回、原图不被误改。
- 资源：真实 RAW 生成代理与导出的峰值内存，编辑期间索引/导出并发，手机温度/电量节流，低内存恢复。
- 构建：先桌面回归，再 Android/iOS 交叉构建、设备安装与真机呈现；模拟器可编译不能替代真机 RAW/GPU 验证。

性能目标沿用 LibRaw 计划中的可见帧口径：常用代理上的轻量调色目标至少 30 fps、输入到可见帧 p95 不超过 100 ms。均为待测目标；白平衡与空间滤镜单独验证，不能用 CPU 函数耗时替代实际呈现。

## 6. 不需要重做的部分与工作量

保留配方作为编辑真值、SQLite 业务关系、评级/相册/分组、PhotoCraft 调色/蒙版/合成算法、已有 LUT 解析、元数据编码及桌面设备接口。修改它们的来源/输出入口与资源策略，不逐项重写数学算法。

粗估按一名熟悉项目、Rust 与移动原生桥接的开发者计算：P0–P2 的基础抽象约 3–5 人周；P3/P4 与 LibRaw/胶片计划重叠，沿用约 3–6 人周估算并在原型后修订；P5 的双平台适配和真机验证另需约 4–8 人周。不能直接把各项相加当成交付承诺，原生构建、GPU 表面和大 RAW 峰值内存是主要不确定项。AI 等 P6 不计入首期。

## 7. 当前建议

先实施 P0/P1：用现有桌面本地文件和一个无路径假来源证明资产访问合同，迁移编辑打开、缩略图和元数据这一条完整流程。随后引入生命周期/资源预算，再按 LibRaw 计划接代理和胶片。这样会把移动端需要的抽象放在实际调用处，同时保持桌面可用，不先重写整个应用。
