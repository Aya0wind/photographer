# 高级编辑预览性能优化

日期：2026-10-09。范围：现有 React/Konva WebView 与 PhotoCraft 原生处理链。原生画布暂不做；本次没有运行、构建或性能测试，不能给出帧率或加速百分比。

## 处理路径

```text
UI 配方变化（忽略仅输出偏好变化）
  → 最新值调度 + 修订号
  → 800/1600 代理各自的原生 Session
  → 缓存曝光/白平衡前缀、增量调整层、几何与独立标注
  → 原生 GPU 优先合成 / CPU 回退
  → 原生 ICC 与 JPEG 编码
  → 二进制 IPC
  → 浏览器预解码并缓存 HTMLImageElement
  → Konva 直接复用解码帧
```

算法仍来自 PhotoCraft；应用侧只做参数适配、状态与缓存管理。预览与导出的调整层种类、参数和执行顺序来自同一 `adjustment_specs`。最终导出继续原尺寸处理，不用代理代替成片。

## 增量会话与失效规则

每个预览会话有独立的交互/精细 Renderer，持有原生 Session。调整层 ID 在修改参数及暂时禁用/再启用时保留；调用上游参数解析生成原生 Adjustment，更新其内容，不每次重新创建整套调整层。COW 文档/瓦片继续复用。

| 变化 | 失效范围 |
|---|---|
| 基础源文档 / RAW 精细显影结果 | 对应通道的曝光/白平衡与其后处理 |
| 曝光、温度、色调 | Camera Raw 前缀；RAW 精细通道按原生传感器显影更新基础文档 |
| 亮度、对比度、饱和度、HSL、色阶、曲线 | 调整层参数及后续几何/合成；复用 Camera Raw 前缀和独立标注 |
| 裁剪、旋转 | 几何；画布尺寸/像素格式/DPI/ICC 未变化时允许复用标注图层 |
| 文字或笔迹 | 标注；复用前面处理结果 |
| 输出质量/尺寸 | 不影响固定代理预览 |
| 完全相同的预览输入 | 直接返回该通道上一张 JPEG |

独立标注使用同一原生文字/笔刷命令在保留色彩模式/调色板与选区语义的透明文档中生成图层，按原始标注顺序附加到处理后的照片。已有选区时保守地重新生成标注，不用缺少选区指纹的缓存。缓存模板只记录必要元数据，不额外持有全幅源像素。预览 Session 不承担用户撤销：其原生命令 history/journal 被清理，用户撤销仍由前端配方历史管理。某个阶段失败时失效最终状态，下一次不能把残留中间状态当成成功帧。

几何仍使用原生顺序：调色 → 旋转/裁剪 → 标注。本次不为了缓存重排空间滤镜。GPU 的底图和标注图层身份稳定；修改曝光/白平衡仍可能生成新的底图瓦片并上传。

源/目标 ICC 经上游解析后字节完全相同且文档是 RGB 时，省略无意义的 sRGB→sRGB 像素转换；仍标记目标 ICC。其他空间正常走原生转换，没有跳过 RAW ProPhoto 等必要转换。

## 调度、解码与资源释放

- 快速帧和精细帧各最多一个请求在途；定时器分别管理，旧精细请求的收尾不能覆盖交互唤醒。
- 快速帧完成及解码后，有新参数就继续处理最新值；移除固定的 16ms 额外等待。精细帧等待参数至少静止 180ms，且当前快速帧完成。
- 顺序完成的快速帧允许显示，以免持续拖动时完全没有画面更新；不能覆盖更晚的版本或同版本已展示的精细帧。
- 预览图解码完成后才发布 URL。Konva 使用同一个 HTMLImageElement，避免发布后再等另一个加载流程。最近三帧及至多两个在途帧有明确释放路径；未发布、过期、关闭时也回收。
- 后台记录会话最新修订号。等待完整 RAW 显影锁的精细请求进入内核前检查有效性；内核结束和后续阶段边界再次检查。关闭会话标记失效。
- **不是硬取消**：已进入的原生 RAW 内核不能被中途强杀；过期时丢弃结果并避免继续构建/编码。初次源导入仍需等待原生解码/显影，尚未增加渐进首屏。
- 创建代理后尽早释放临时全幅文档；RAW 传感器、GPU 缓存与会话数量的既有预算继续有效。预算不是进程总 RSS 上限。

## 分段诊断

`edit_preview_stats(sessionId)` 返回 `openMs` 与 `interactive/refined` 最近一次尝试的诊断：

| 字段 | 含义 |
|---|---|
| `frames/cachedFrames` | 请求次数、完整 JPEG 缓存命中次数 |
| `frameCacheHit/cameraCacheHit/annotationCacheHit` | 该次请求的阶段命中情况 |
| `rawMs` | 获取/生成 RAW 精细基础文档的阶段耗时，包含等待显影锁；交互通道通常只有适配开销 |
| `cameraMs/adjustmentsMs/geometryMs/annotationsMs` | 预览文档准备与各阶段耗时 |
| `compositeMs` | GPU 合成与读回，或 CPU 回退合成/格式适配耗时 |
| `profileMs/encodeMs` | ICC 处理、原生 JPEG 导出耗时 |
| `totalMs` | 原生预览与 RAW 精细准备耗时；不含全部 IPC 排队/传输及浏览器绘制 |
| `gpu` | 本次实际是否完成 GPU 合成；整帧缓存命中时没有新合成，不能把 `false` 解读为 CPU 回退 |

浏览器 User Timing 保留每类最新样本：

- `editor.preview.interactive.frame-ready`：参数修订到交互帧解码完成并交给 UI 的时间。
- `editor.preview.refined.frame-ready`：参数修订到精细帧就绪，包含静止等待时间。
- `editor.preview.diagnostics`：精细帧之后异步查询诊断的 IPC 时间；`detail` 是原生诊断，不是这个 entry 的 duration。

交互帧不增加诊断查询；每次成功发布精细帧后才异步读一次。可在编辑窗口开发者工具中查看：

```js
performance.getEntriesByName("editor.preview.interactive.frame-ready").slice(-1)[0]?.duration
performance.getEntriesByName("editor.preview.diagnostics").slice(-1)[0]?.detail
```

需要连续样本时用 PerformanceObserver 收集这些 measure。`frame-ready` **不等于已经绘制到屏幕**；真实呈现时间、FPS、p95 和长任务要结合浏览器性能记录与实机测量，不能直接把一帧耗时换算成持续帧率。

## 尚未实施与下一步依据

本次没有引入原生绘制区域、原尺寸编辑母版持久化、1:1 ROI、损坏区域/瓦片传输、动态代理尺寸或全 CPU 调度优先级。这些仍在 Roadmap 中，根据分段数据选择：

- Camera Raw/RAW 阶段占大头：优先代理/区域显影、预取和资源调度，复用上游实现。
- 几何/合成占大头：优先缓存、视口和损坏区域更新。
- JPEG/IPC/浏览器解码占大头：比较局部传输、二进制像素与现有压缩图；未实测不假设 RGBA 更快。
- 绘制本身占大头且原生路径有明确收益：再评估原生画布，不因“原生”一词就替换。

## 验证边界

本次仅 TypeScript 类型检查、Rustfmt 格式/语法解析、锁文件元数据与差异/接口静态审查。Rust 类型/链接、GPU 表现和预览一致性未通过本次本地构建或运行确认。

后续实机重点：快速拖动且精细显影在途；拖动中切图/关窗；RAW 参数归零和撤销/重做；曲线/HSL 改动时前缀命中；标注调色时缓存命中，改变裁剪尺寸时失效；输出偏好不触发预览；有/无 GPU；RGB/灰度/CMYK、高位深与带 ICC 照片；缓存错误后重试；JPEG 缓存命中及 sRGB 身份转换。对比默认重建路径的预览/成片，不把减少调用次数当成已经获得某个加速比例。
